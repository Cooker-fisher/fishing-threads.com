# Codex連携ルール

この文書は、このプロジェクトで Codex をどう使うかを定義する。

## このプロジェクトにおけるCodexの位置づけ
Codex は**実装担当**であり、**プロダクト設計責任者ではない**。

つまり：
- まず文書で設計を固定する
- Codex はそのルール内で実装する
- Codex が勝手に schema、命名、プロジェクト方向を再定義してはいけない

## Codexが向いている仕事
このプロジェクトで Codex に向いている作業：
- 確定済み内容に基づく docs 更新
- ディレクトリ雛形作成
- 1ページ種別に対する extractor 実装
- テスト追加
- 局所的なリファクタ
- 合意済みschemaに沿った sample JSON 生成
- 限定的なバグ修正

## Codexに決めさせないこと
次は文書で先に決めるべきであり、Codex単独で決めさせない。
- プロダクトの中核方向
- raw / normalized / derived の境界
- 命名体系の変更
- relation / setup のアーキテクチャ変更
- 新しい釣具カテゴリへの拡張判断
- ストレージ方針変更
- repo運用方針変更

## 運用モード
Codexは2モードで使う。

### 1. Askモード
使う場面：
- repoの見慣れない部分を理解したい時
- 実装前に影響範囲を確認したい時
- 複数案を比較したい時

### 2. Codeモード
使う場面：
- タスクの範囲がすでに狭い時
- 対象ファイルが分かっている時
- acceptance criteria が明確な時

## Codexに渡すべき情報
小さくないタスクでは最低限これを渡す。
- 目的
- 対象ファイル
- 変更してはいけないもの
- acceptance criteria
- docs-only / extractor-only / schema-only / UI-only のどれか

## タスク粒度ルール
次のような広すぎる指示は避ける。
- `サイトを作って`
- `DB設計して`
- `全体を整えて`

代わりに、狭い指示にする。
例：
- `Shimano電動リール一覧extractorを scripts/... に実装`
- `docs/raw-examples/ に raw JSONサンプルを追加`
- `repo-structure文書を現状フォルダに合わせて更新`

## Codex作業のPRルール
Codexで作った変更もPRで入れる。
理想は **1タスク = 1PR**。

## Codex成果物のレビュー観点
merge前に確認する。
- 文書化済みアーキテクチャに沿っているか
- 意図した層だけを触っているか
- rawを早すぎる段階で正規化していないか
- 重いファイルやノイズを入れていないか
- 承認なしに命名変更していないか

## このプロジェクトでの初期Codex用途
初期は以下に寄せる。
- docs更新
- rawサンプル
- extractor雛形
- セレクタベース抽出
- schema検証補助

いきなり広範囲の自律的プロダクト構築に使わない。

## まとめ
Codex は、設計が固定された後の実装を加速するために使う。
プロジェクト構造の正本にはしない。
